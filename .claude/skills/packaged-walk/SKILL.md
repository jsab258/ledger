# The packaged build and the AI tester's walk

Why: CLAUDE.md ("How the work is done"): every piece changed in a day is walked by the AI tester in that night's packaged build; a piece passes only there, offline checks are screens. The gate (.claude/skills/gate/SKILL.md, step 8) and the garment skill (.claude/skills/game-garment/SKILL.md, step 9) end here. Every step names its source: a tool's own usage text, the build machine's workflow (.github/workflows/ledger-probe-unreal.yml) or a lesson in Claude's memory notes (C:\Users\Jafar\.claude\projects\C--Users-Jafar-ledger-local\memory\, by file name). "Check first" marks what the sources do not settle.

**Always** (none of these bends):
- One Unreal job on this PC at a time. The build machine (the GitHub runner, Runner.Worker, under C:\actions-runner-ledger) shares the one engine install, so a local UnrealEditor (even a -game run), Build.bat or UnrealBuildTool during its build breaks it with ConflictingInstance or OtherCompilationError (CLAUDE.md: two Unreal builds never overlap; editor-blocks-runner-build).
- Room first, before any build, render or game run: `python tools/retention.py space --job "what" --drives CF`. STOP means stop: the job goes into Needs you and is not retried (CLAUDE.md; tools/retention.py, whose own defaults `--need-c 40 --need-f 20` set the floors; build-local.ps1 checks C: only, since compiling writes only there).
- A piece passes only in the packaged copy (F:\LedgerTools\played-game) walked by the tester; editor runs and offline checks are screens, necessary and never enough.
- The tester sends real key presses and mouse moves to the game window (tools/ai-tester/play.py). Only the session runs it or route_walk.py; helpers never send clicks or keys (CLAUDE.md; MEMORY.md, helper-briefs-forbid-clicks). Nobody should be at the PC: `start` refuses when it was used in the last two minutes.
- No local GPU work while the build machine's job or the walk runs: on 29 Sep a shared card made its frame test read about 15 fps instead of 70, which looked like a regression (local-renders-spoil-runner-fps).
- Two tries per fault, then research; a third try needs Jafar's yes first (CLAUDE.md).

**Requests this covers**, for example: "get this into tonight's build"; "build me a packaged copy now, as the step's evidence"; "did last night's walk play today's work?"; "the build machine went red, why?"; "walk the new seat in the packaged game"; "film the stretch for his page"; "it works in the editor but not packaged"; "can I run the editor now?".

## 1. Make the change packageable

- A packaged copy reads its run-time files only from its Content/LedgerData, which tools/ue/stage_game_data.py fills from its FIXED list and the folders it computes. The editor also finds them beside the repository, so a file missing from the list works in every local run and fails only packaged (30 Sep: a red golden row from an unlisted spec). Any new file the game reads under production/specs or content/ goes into that list in the same commit (packaged-copy-needs-ledgerrepo). Pictures the game reads live on F:\LedgerTools\game-inputs under their repository path, since git takes none outside production/previews (stage_game_data.py, GAME_INPUTS).
- Any C++ change under ue-probe/Source: build both targets before the push, `powershell.exe -NoProfile -File tools/ue/build-local.ps1` (editor target, then game target; it waits while the build machine builds and runs the space check for C: itself). The editor build hides editor-only calls that break the build machine's game build (26 Sep; build-game-target-before-push).
- A build that fails in about a second with RulesError: read UnrealBuildTool's Log.txt (%LOCALAPPDATA%\UnrealBuildTool) for a plugin the Epic launcher just changed, and switch that plugin off in ue-probe/LedgerProbe.uproject; never touch the engine (epic-fab-update-breaks-build).
- Unreal settings every program must see go in through the workflow's step "Install this project's Unreal cache settings", never by writing AppData from here: what Claude writes there only Claude sees (appdata-writes-are-private-to-claude).
- **Check:** the new path is in stage_game_data.py's FIXED list and `python tools/ue/stage_game_data.py --list` prints missing=0 (it exits 1 when anything is missing); build-local.ps1 ends with "both targets built".

## 2. Room and a free machine

- The space check above, with the job named, before every build, render or run; its line lands in F:/LedgerTools/retention/space-checks.log (retention.py).
- The build machine idle: no Runner.Worker.exe in `tasklist /FI "IMAGENAME eq Runner.Worker.exe"` (the check tools/nightly_walk.py and `play.py start --editor` use; the packaged `play.py start` waits only for the build machine's own game or Unreal processes). For GPU work wait for the whole job, not only its Unreal processes: its frame and game steps run after the compile (local-renders-spoil-runner-fps). Runner.Worker vanishes for a moment between two queued runs, so for heavy GPU work check twice, a minute apart, and re-check before each launch in a loop; another session can start a build at any moment (editor-blocks-runner-build).
- The night jobs: read their times from Task Scheduler in PowerShell, `Get-ScheduledTask | ? TaskName -like "*LEDGER*" | Get-ScheduledTaskInfo`, and stop local Unreal about 15 minutes before the walk and the morning pictures (night-jobs-local-times; read 29 Oct: walk 01:30, retention 03:30, morning pictures 04:15; the tools' own docstrings say 02:30, 04:30 and 05:15 and are out of date). Read the clock with PowerShell's Get-Date, not Git Bash's date, which is an hour behind (MEMORY.md, read-swiss-time-with-powershell).
- No game left open: `python tools/close_games.py --dry-run` names any (the packaged launcher and its child, editor -game runs), `python tools/close_games.py` closes them. Stopping only the launcher F:\LedgerTools\played-game\Windows\LedgerProbe.exe leaves LedgerProbe\Binaries\Win64\LedgerProbe.exe running; close by tree (`taskkill /PID <launcher> /T /F`) (packaged-game-child-survives). After `play.py close` on an editor run, UnrealEditor.exe lingers up to about 40 s; wait for it to go before building (tester-editor-exits-late).
- Marvelous and Blender holding the card spoil the frame test (tools/close_games.py, CARD_HOLDERS, 27 Oct: 78 fps fell to 22); they are his programs and are named, never closed by a script. Marvelous is closed only for a build, and he is told (MEMORY.md, marvelous-holds-card-memory).
- **Check:** the space verdict GO; no Runner.Worker, UnrealEditor or LedgerProbe process; outside the 15 minutes before a night job.

## 3. Push it so the build machine can build it

- Push only what passed its checks: capture the last line of `bash tools/ci-checks.sh` and push only when it reads failed=none, as in `out=$(bash tools/ci-checks.sh 2>&1 | tail -1); echo "$out"; case "$out" in *failed=none*) <the push>;; esac`. Piping into `&& git push` pushes on red, because the pipe's exit is tail's (gate-push-on-failed-none). Chain any rebase before the checks, so a stopped rebase never reaches them.
- `unset MSYS_NO_PATHCONV` before the checks: set for Unreal launches, it gives false reds (42/44) (unset-msys-before-ci-checks).
- No `git rebase --autostash` while UnrealEditor runs: it holds uassets open and leaves the repository mid-rebase; if it happens, `git rebase --quit` (no-rebase-while-unreal-runs).
- Flatten any merge whose side branch forks from far back into a plain commit before pushing: a shallow build machine fetched 28 GB of history for one and filled C: (deep-merge-fills-c).
- **Check:** the checks' line read failed=none before the push ran; the push was not refused by the push guard.

## 4. Ask for the packaged build

- The workflow builds only on a manual dispatch, a push to main, or a wip push whose last commit's message carries [package] (its `if:` reads `github.event.head_commit.message`, so a [package] commit with another pushed on top of it builds nothing). And only if the push touches a path it watches (`on: push: paths:`): ue-probe/**, tools/ue/**, ledger/TalkHelper/**, ledger/Assets/Scripts/Core/**, the workflow itself, production/specs/**, production/assets/street, people, vehicles, sounds and steps, tools/runner/**, production/d1-probe/PACKAGE.md. A plain wip push shows the job "skipped" by design: not a stuck runner, never restarted for that (package-request-needs-watched-path).
- The sure way: `python tools/nightly_package.py` (`--dry-run` says what it would do). It asks only when wip has moved since the played copy's commit, appends one line to production/d1-probe/PACKAGE.md in a [package] commit made without touching the working tree, and pushes it. It works from origin/wip, so local commits must be pushed first. The nightly walk calls it itself; the workflow's comment also names a Windows task "LEDGER nightly package", which the 29 Oct reading of Task Scheduler did not list: check first.
- Push nothing more while that run waits: the workflow's concurrency group replaces a waiting run with the newer one (the running one is never cancelled).
- **Check:** it printed nightlyPackage=ASKED (or UP-TO-DATE: the played copy already holds wip); Runner.Worker appears within a few minutes.

## 5. What the build machine does: read it, never drive it

- In order (the workflow's step names): "Check free space on C and F"; "Wait for this PC's own Unreal work to finish" (up to 40 minutes, then it goes ahead); "Build the UE probe target and run the golden test": the game target, cold then warm (coldBuildExit is the cold build's exit), the editor target, the base material made by tools/ue/make_base_material.py through UnrealEditor-Cmd, stage_game_data.py, then `RunUAT.bat BuildCookRun ... -cook -build -stage -pak -archive` into ue-probe/Packaged; "Ship the talk program inside the package"; "Copy the packaged build to a stable path" (F:\LedgerTools\played-game, only when the build step succeeded; games running from the copy closed first); its own shots, walk, crime and encounter tests; "Commit the probe result" to production/d1-probe/ on the built branch; the leftovers cleared.
- It runs as Jafar from his Startup folder (LEDGER runner.lnk), not as a service; tools/runner/reconnect.ps1 restarts it (runner-no-password-startup). Check first that it is really offline before any restart: a skipped job is not a stopped runner (step 4).
- A green run does not prove the played copy was replaced: the copy step is continue-on-error, and when the old copy is locked it reports OLD-COPY-LOCKED only in the run's summary, leaving the old stamp file. A run stopped by the space check commits nothing, so ue-build.txt stays the previous run's; the reason is in F:/LedgerTools/retention/space-checks.log and the run's error line.
- **Check:** production/d1-probe/ue-build.txt (fetched after its "UE machine probe from" commit) shows coldBuildExit=0, probeTest=PASS and buildReached=end, the three "The build decides the colour of the run" reads; the first line of F:\LedgerTools\played-game\LEDGER-STABLE-COPY.txt ("# LEDGER stable build copy <sha>") names the built commit, and F:\LedgerTools\played-game\Windows\LedgerProbe\Content\LedgerData\build-commit.txt is the pushed commit or later. A failed build leaves the old copy, and the walk then plays the old game: say so in the summary.

## 6. The nightly walk

- Task Scheduler's "LEDGER nightly walk" runs `python tools/nightly_walk.py`: it closes games left open, asks for the package (step 4), waits up to 90 minutes for the build machine, walks the played copy with `tools/route_walk.py --town`, runs the bench and the eyes, and writes production/playtest/nightly/<date>.json and .md. The night's folder F:/LedgerTools/nightly/<date> holds route/verdict.json, walk.log, the bench and state.json; the tester's step pictures are in production/playtest/ai-tester/<time>/ (gitignored), where the report reads them. `--report-only` writes the report again from that night's files.
- It waits 90 minutes for the build machine and then walks anyway: if the build is still running, the walk plays the old copy, and the build's copy step closes any game running from the played copy, ending the walk mid-run (nightly_walk.py main; the workflow's stable-copy step). A late build is named in the summary, not read as a fault in the piece.
- The session's part: the day's work, C++ included, pushed to wip before the walk, or the night's build cannot carry it (night-jobs-local-times); local Unreal stopped about 15 minutes before; the PC left alone during the walk.
- The night route reaches only its own stages (route_walk.py's docstring lists them). A piece off that route (a room, a seat, a garment seen close) needs its own packaged run by day (step 7) or a change to nightly_walk.py's route call (it passes only `--town --out`); check first which stages reach it.
- **Check:** the report's walk line (stages passed of stages, the failed ones named) and its "what broke" lines read; the night report records no build commit, so compare the played copy's stamp time with the walk's start (the tester folders' times, such as 2026-11-02-0202): check first, since a later build may have replaced the copy after the walk.

## 7. The session's own packaged runs

- The route: `python tools/route_walk.py [--town] [--sit] [--out DIR] [--game-arg -Switch ...]`, on the played copy; verdict.json, pass or fail per stage, in production/playtest/route-walk/<stamp> by default; exit 0 only when every stage passed. Its `--editor` form, and `play.py start --editor`, refuse while Runner.Worker runs, and count only as screens.
- Free play: `python tools/ai-tester/play.py start [--wait 60] [--game-arg X] [--packaged EXE]`, then `shot`, `walk forward|back|left|right SECONDS [--run] [--film]`, `turn DEGREES`, `press E|T|Z|Esc|Q|Enter|Up|Down`, `say "WORDS"`, `wait SECONDS`, `note SEVERITY "WHAT"` (5 unplayable to 1 cosmetic), `finish "SUMMARY"`, `close`. Look at each picture before the next command. It writes production/playtest/ai-tester/<time>/ (each step's picture, report.md worst first, for-jafar.md); its talk is the stand-in (-TalkFake) unless `start --real-talk` (packaged only, under a budget cap, the game reading its own key); the tester itself never reads or passes a key.
- Never hold the game's files open during a walk: no tail or Monitor on Saved/route-checks.jsonl, which stops the game appending its lines (29 Oct: a walk failed "no street line"). Wait for the walk's own command, then read; after stopping a Monitor, end any tail.exe it left (never-tail-route-checks).
- A film: `walk ... --film` keeps about eight frames a second in F:/LedgerTools/tmp/ai-tester/film/<run>/; `play.py film` stitches them into one GIF. For his page, one stretch as WebP, only frames a fresh reviewer has checked (film_webp.py): `python tools/film_webp.py FILM_DIR FIRST LAST OUT.webp [--width 800] [--ms 125]`, or by name, `python tools/film_webp.py FILM_DIR --marks production/playtest/route-walk/<run>/film-marks.json --name NAME OUT.webp`, where film-marks.json exists only after a route walk that filmed named stretches (`--sit`, or route_walk.py's `--camera`, which its usage line does not list: check first). Faces are filmed with the game's own switches (-FaceAB, -AskScript), not by walking to people (tester-editor-exits-late).
- Afterwards `python tools/close_games.py --dry-run` names nothing left running (`play.py close` stops its own process without /T).
- **Check:** every stage's verdict and every note read, each fault with its picture; nothing left running.

## 8. Editor runs: screens before the packaged check

- The editor's game mode needs the street's switches, copied from tools/p1-packaged.ps1: `-LedgerSlice -LedgerCrime -Encounter=live -LiveFresh -TalkFake -NoTitle`, with `-RenderOffScreen -ResX=2560 -ResY=1440 -LedgerRepo=<checkout>` for pictures; without them it waits silently on the title or never starts the street (editor-photographs-need-the-street). Add `"-ExecCmds=scalability 2"`: the game ships at High, and on 26 Oct a room passed every editor review at the Epic level and failed packaged (photograph-at-the-played-level).
- From Git Bash, `export MSYS_NO_PATHCONV=1` before any launch with /Game/ paths, or launch from PowerShell; unset it again before the checks (git-bash-rewrites-asset-paths).
- Give an editor run 600 s and read its own result line, never the exit: the first run after a rebuild needs about three minutes to its first frame (editor-game-first-run-slow). The first run after a street re-import rebuilds its caches for over 25 minutes, so give it a limit well beyond that (editor-photographs-need-the-street).
- Walk measurements and pictures on a fixed step, `-benchmark -fps=60`, or screenshots stall frames and change the walk; judge the worst steps by eye through a fresh reviewer (walk-pictures-need-fixed-step).
- The packaged frame-and-memory profile: `powershell -File tools/p1-packaged.ps1` (three 1800-frame captures, day standing, night standing, day walking, at 3440x1440, with the voice speaking beside the game; one line each to production/research/pre-production/p1-packaged/runs.jsonl; `-Only` keeps named captures, `-Voice none` leaves the voice out). It refuses while the build machine, an editor or a game runs, and sets the picture level itself (`-Picture`, default 2, High).
- **Check:** each editor result is recorded as a screen, and the piece still goes through steps 4 to 7.

## 9. Reading the result

- In the morning, before any summary: the night's report, any tester run's report.md, and ue-build.txt when the build was red (its error lines come from the whole cook log). A frame rate that drops sharply: first ask whether local GPU work overlapped the run (local-renders-spoil-runner-fps).
- A new fault in the piece blocks it: fix it (two tries), push, walk again. The piece is "done" only when a packaged walk names no new fault in it; a big item stays "ready for review" until Jafar passes it (CLAUDE.md).
- The pass ran on the player's own launch line: `python tools/launch_line_check.py <the run's game log>` prints PLAYER or PLAYER+WATCH; TEST names the test switches and the run is not a pass (8 Nov: the office and sitting "passed" for days behind -MickeysInside and -TomSit). Its notes (stand-in talk, a camera mode) go beside the verdict.
- **Check:** the walk that passed the piece played a copy whose build-commit holds the piece's commit (its time compared with the walk's, as in step 6); launch_line_check said PLAYER or PLAYER+WATCH for its log.

## Records

- FINDINGS.md: each open fault the walk found, until fixed. FOR-JAFAR.md: the tester's paragraph from the night's report by 07:30, what failed named (CLAUDE.md; tools/nightly_walk.py). A build the night could not make, or a walk of an old copy, is said plainly there.
- DECISIONS.md one line per material choice; the time against the item (tools/timelog.py), helpers' too; RECIPE.md a few setting-free lines when the unit finishes; reports and verdicts in production/playtest/ (the tester's pictures there are gitignored), films on F:/LedgerTools/tmp/ai-tester/film, previews for git only as production/previews/ JPEGs.
