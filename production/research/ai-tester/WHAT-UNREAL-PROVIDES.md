# Exploratory AI tester: what Unreal 5.8 already provides

Researched 2026-09-23. I read the engine installed on this PC and Epic's 5.8 documentation. Below, `E\` means `C:\Program Files\Epic Games\UE_5.8\Engine` and `G\` means `E\Source\Programs\AutomationTool\Gauntlet`.

## What exists

**Gauntlet (the `RunUnreal` command).** This starts an already-packaged build, watches it while it runs, and writes up the result. It works on this PC. When no device is named, it creates "LocalDevice" entries for the machine it is running on (`G\Framework\Devices\Gauntlet.DevicePool.cs`, `AddLocalDevices`). Its options include `-build=`, `-test=`, `-platform=`, `-configuration=`, `-windowed`, `-ResX/-ResY`, `-MaxDuration`, `-ClientArgs=`, `-ExecCmds=` and `-LogDir=` (`G\Unreal\RunUnreal.cs`). Unless told otherwise it runs the game in a 1280x720 window (`G\Unreal\Base\Gauntlet.UnrealTestConfiguration.cs`). When a run ends, it copies the logs and crash dumps into an artifact folder. It then sorts the exit into one of these: fatal error, engine failed to start, ensures, killed at the time limit, a normal requested exit, or "unhandled reason" (`G\Unreal\Base\Gauntlet.UnrealTestNode.cs`, `GetExitCodeAndReason`). A test is a C# class based on `UnrealTestNode<UnrealTestConfig>`. The built-in `UnrealGame.DefaultTest` starts one client and waits until it exits or times out, so no custom C# is needed (`G\Unreal\Game\UnrealGame.DefaultNode.cs`). Gauntlet is already compiled in this launcher install (`E\Binaries\DotNET\AutomationTool\AutomationScripts\Gauntlet\net10.0\Gauntlet.Automation.dll`) and runs through `E\Build\BatchFiles\RunUAT.bat`. Docs: https://dev.epicgames.com/documentation/en-us/unreal-engine/running-gauntlet-tests-in-unreal-engine and https://dev.epicgames.com/documentation/en-us/unreal-engine/gauntlet-automation-framework-overview-in-unreal-engine

**The in-game half of Gauntlet (the Gauntlet plugin; beta, off by default).** It lives in `E\Plugins\Experimental\Gauntlet`. You choose a C++ "test controller" with `-gauntlet=Name`. It reports game states and heartbeats, and Gauntlet can stop a run whose heartbeats stop arriving. It can also take a screenshot at a set interval with `-gauntlet.screenshotperiod=` (`...\Public\GauntletTestController.h`, `...\Private\GauntletModule.cpp`). This is code inside the game, so it is the kind of driving the owner wants to avoid, and nothing in it is needed here.

**Gauntlet pressing keys through the network (unfinished).** Gauntlet's C# side has an `InputAction` (a key, pressed or released, plus a mouse movement) that it sends to the game as a web request (`G\Framework\Utils\Gauntlet.InputActions.cs`, `G\Framework\RpcFramework\`). The engine has the receiver that listens for these requests (`-rpcport=`), and it is compiled out of Shipping builds (`E\Source\Runtime\ExternalRPCRegistry\Public\ExternalRpcRegistrationComponent.h`). However, no engine code handles input requests. The only engine requests are the Automation Controller's five (`E\Plugins\AutomationControllerRpc\Source\AutomationControllerRpc\Private\AutomationControllerRpcRegistrationComponent.cpp`), and a comment in the library says it is the general part of Fortnite's system and "will eventually be moved to the engine" (`G\Framework\RpcFramework\Gauntlet.RpcLibrary.cs`). So Gauntlet cannot press keys in our game as shipped, and making it do so would mean writing code inside the game.

**Automation Driver.** It lives in `E\Source\Developer\AutomationDriver` and only works inside the game process. It replaces the handler that passes Windows input to Slate (Unreal's UI layer) with its own. The header says that turning it on "causes most traditional input messages from the platform to stop being received" (`Public\IAutomationDriverModule.h`). It is designed for C++ tests that click and type into UI widgets found by their tag or path. It cannot drive a packaged game from outside. While it is on, it would also block the Windows-level input an outside agent sends. Docs: https://dev.epicgames.com/documentation/en-us/unreal-engine/automation-driver-in-unreal-engine

**Automation System, Automation Spec, Functional Tests and Session Frontend.** Every non-Shipping game build includes the test runner (`AutomationWorker`) and `FunctionalTesting` (`E\Source\Runtime\Launch\Launch.Build.cs`). That means a Development build of LedgerProbe.exe can run them with `-ExecCmds="Automation RunTests <name>;Quit"` (the commands are in `E\Source\Developer\AutomationController\Private\AutomationCommandline.cpp`; docs: https://dev.epicgames.com/documentation/en-us/unreal-engine/run-automation-tests-in-unreal-engine). Specs are C++ tests. Functional tests are actors placed in a level: each one scripts a scenario and passes or fails (https://dev.epicgames.com/documentation/en-us/unreal-engine/functional-testing-in-unreal-engine). Session Frontend is an editor window that lists these tests and runs them on a connected editor or game (https://dev.epicgames.com/documentation/en-us/unreal-engine/automation-system-user-guide-in-unreal-engine). All of these are checks scripted in advance, the same kind as -LedgerWalk. None of them explores.

**Screenshot Comparison.** Screenshot tests save images to `Saved\Automation\Comparisons`, and Session Frontend compares each one with an approved "ground truth" image (https://dev.epicgames.com/documentation/en-us/unreal-engine/screenshot-comparison-tool-in-unreal-engine; source in `E\Source\Developer\ScreenShotComparison*` and `G\Framework\Utils\Gauntlet.ScreenshotCompare.cs`). It suits fixed camera positions, not a player wandering around.

**Remote Control API.** It lives in `E\Plugins\VirtualProduction\RemoteControl`. It is a web server inside the game that can read and set object properties and call functions (`/remote/object/property`, `/remote/object/call`). Outside the editor it stays off unless the game is started with `-RCWebControlEnable` (`...\WebRemoteControl\Private\WebRemoteControl.cpp` line 342; https://dev.epicgames.com/documentation/en-us/unreal-engine/remote-control-for-unreal-engine). It works by calling into the game's code, so at most it could read the player's position to check the agent's guess. It should not be used for driving.

**Command line, console, log, crashes and traces.** `-ExecCmds=` runs console commands when the game starts, and the console is available in Development builds. `-stdout -FullStdOutLogOutput` and `-abslog=<path>` give a log file the agent can read, and the probe already uses the log flags. A crash writes a folder under `Saved\Crashes` containing the log, a minidump and `CrashContext.runtime-xml` (https://docs.bugsplat.com/introduction/getting-started/integrations/game-development/unreal-engine). `-unattended` stops dialog boxes from waiting for a click. Unreal Insights records a `.utrace` file when started with `-trace=default` in a Development build (https://dev.epicgames.com/documentation/en-us/unreal-engine/trace-quick-start-guide-in-unreal-engine).

**Bots, replays and the Gameplay Debugger.** Epic ships no general play-testing bot. The only "bot" in this install is Fortnite's `FortClientBot`, which appears in a sample log in Gauntlet's self-test data (`G\SelfTest\TestData\LogParser\Win64FatalError.txt`). Gauntlet's game samples are a Fortnite GPU performance test and ElementalDemo (`G\Unreal\Game\Samples\`). The replay system records only what the game sends through replication, the system Unreal uses to sync game state over a network, so it records single-player games only if they are set up that way. I have not checked whether LedgerProbe is (https://dev.epicgames.com/documentation/en-us/unreal-engine/using-the-replay-system-in-unreal-engine). The Gameplay Debugger is compiled into Development game builds by default (`bUseGameplayDebugger` in `E\Source\Programs\UnrealBuildTool\Configuration\Rules\TargetRules.cs`). The apostrophe key shows AI and perception state on screen, which the agent could photograph (https://dev.epicgames.com/documentation/en-us/unreal-engine/using-the-gameplay-debugger-in-unreal-engine).

## What fits this job, and how the pieces combine

1. **Gauntlet launches and supervises.** Run `RunUAT RunUnreal -test=UnrealGame.DefaultTest -project=<LedgerProbe.uproject> -build=<archived Windows folder> -platform=Win64 -configuration=Development -windowed -ResX=1280 -ResY=720 -MaxDuration=<seconds> -ClientArgs="-nosplash -abslog=<path>"`. This starts LedgerProbe.exe on this PC, kills it at the time limit, and afterwards returns the log, any crash dump and a verdict: normal exit, timeout, crash, fatal error or failed start. For a first version this needs no C# and no plugin.
2. **A computer-use agent looks and presses keys.** Nothing in Unreal can do this from outside the game. The agent runs in Jafar's logged-in desktop. It takes screenshots of the game window and sends Windows `SendInput` key presses and mouse movements. Afterwards it writes up bugs, dead ends, controls that did not respond, places it could not get out of, and anything that looked wrong. It ends a run by quitting the game normally, which Gauntlet counts as "exit requested, OK". If it forgets, Gauntlet times the run out.
3. **What the game has to provide. All of it is launch flags or existing settings, with no new game code:**
   - A **Development** build. Shipping removes the console, the automation runner, the Gameplay Debugger and the mouse setting below.
   - A **visible window at a fixed size**. It must not be started with `-RenderOffScreen`, which the probe uses. Gauntlet's `-windowed -ResX -ResY` covers this.
   - **A known starting state.** Each run is a fresh launch. Gauntlet also clears the device's artifacts between runs by default (`SkipCleanDeviceArtifacts` in `Gauntlet.UnrealTestConfiguration.cs` is off unless set).
   - **A log the agent can read during the run.** Use `-abslog=<fixed path>` to catch errors as they happen, in addition to Gauntlet's copy at the end.
   - **Keys reach the game as ordinary Windows messages.** Unreal registers raw input for the mouse only (`E\Source\Runtime\ApplicationCore\Private\Windows\WindowsApplication.cpp`, `HandleRegister` and `RegisterHighPrecisionMouseMode`), so `SendInput` keys work as long as the game window has focus.
   - **Mouse-look needs relative mouse movement.** While the game holds the mouse (it does from launch: `bCaptureMouseOnLaunch=true` and `CapturePermanently_IncludingInitialMouseDown` in `E\Source\Runtime\Engine\Private\UserInterface\InputSettings.cpp`), it turns the camera only from relative raw mouse movement. An absolute "move the pointer to x,y", which many computer-use tools send, is treated as a pointer position and not as a turn, and `SetCursorPos` produces no raw input at all (`WindowsApplication.cpp`, the `WM_INPUT` handling). The fix is either to send relative movements, or to start the game with `-ExecCmds="Slate.ForceRawInputSimulation 1"`. That setting, which exists only in non-Shipping builds, converts absolute movements into camera turns the same way Unreal does over Remote Desktop (`WindowsApplication.cpp` lines 837-845, 1185-1188 and `ProcessRawMouseInput`).
   - **Losing focus.** The game keeps running (`bPauseOnLossOfFocus=false` in `E\Config\BaseEngine.ini`, and `t.IdleWhenNotForeground` defaults to 0). However, any held key is released (`bShouldFlushPressedKeysOnViewportFocusLost=true` in `InputSettings.cpp`), and the mouse is let go until the window is clicked again. The agent must click the window to take focus before acting and after anything pops up.

## What does not exist and would have to be built (the smallest version)

- **The agent loop and its report.** A computer-use loop that screenshots, decides, presses and takes notes, then writes the findings as markdown next to Gauntlet's artifact folder. This is the whole of the new work.
- **A short launcher script** of about 30 lines of PowerShell. It starts `RunUAT RunUnreal ... UnrealGame.DefaultTest` in the background, waits for the LedgerProbe window, starts the agent, and at the end puts Gauntlet's verdict, log and crash files together with the agent's notes.
- **Not needed for version one:** a C# Gauntlet test (only needed for custom pass/fail rules), anything inside the game, the Gauntlet plugin, Remote Control, or the Automation Driver. Add a line to the game's log reporting the player's position only if the agent turns out unable to tell whether it is stuck. That would be for watching only, never for driving.

## Open risks

- **It needs the real, unlocked desktop.** Right now the runner is a console process in Jafar's logged-in session (session 1). Its Windows service is installed but stopped. If that service is ever started, jobs run in session 0, and Microsoft says "Services cannot directly interact with a user as of Windows Vista" (https://learn.microsoft.com/en-us/windows/win32/services/interactive-services). The agent would then see and press nothing. A locked screen, sleep or the screensaver also stops it. While the agent runs, it owns the mouse and keyboard, so Jafar cannot use the PC.
- **Mismatched administrator rights fail silently.** `SendInput` does not reach a process running with higher rights, and it reports no error (https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-sendinput). The agent and the game must be started at the same level.
- **Absolute mouse moves do not turn the camera** (see above). If this is missed, the first "bug" the agent reports will be that the camera does not move.
- **The world does not wait while the agent thinks.** It takes seconds per step, and the game keeps running meanwhile. Timed events, and anything the crime or the witnesses do on a clock, can pass while it thinks, and it may report that as a bug.
- **Anything else can take focus.** A Windows notification, an update prompt or another window takes focus and releases held keys.
- **Sharing the PC with the probe.** A run does not build, so the rule against two overlapping Unreal builds does not apply. It does compete with a probe run for the GPU and the screen, so the two runs should take turns.
- **Unverified here:** that Gauntlet accepts the probe's archived folder layout as `-build=`. `RunUnreal` has not been run on this PC yet, and the first try is where that will show.
- **Not a starting point:** the repo's existing "LEDGER AI playtest" workflow runs the older C# simulation harness on a GitHub-hosted Linux machine, not the packaged game.
