# Our MetaHuman as the avatar in Marvelous Designer (26 October 2026)

The question: Marvelous Designer (MD) 2026.1.237 Personal imported Tom's MetaHuman body (MH_TomL1_FullBody.fbx) by script with `bAddArrangementPoints=True`, and said "Arrangement Points were not fitted to the avatar. The avatar must be in a T-pose or A-pose." What does MD need, how else can points be had, what does the MetaHuman DNA importer give, and how does a garment simulated in MD reach the game skeleton's bind pose?

All web sources were read on 26 October 2026 (numbers in brackets point to the list at the end). D = documented by CLO or Epic; M = measured on this PC without opening MD; I = inference; UNVERIFIED = not confirmed. This updates production/research/clothing-pipeline/MD-AVATAR-ARRANGEMENT-2026-10-02.md, which was written before the scale finding below.

## Short answers

1. **The likely cause is scale, not pose (I, strong).** On 2 October our own jobs found that MD reads these centimetre FBX bodies as millimetres when `scale` is 1.0, so the body comes in ten times too small; scale 10 fixed it [12]. Every arrangement-point attempt so far ran at scale 1.0: the three of 1 and 2 October (learn1, avatar_try) and today's import_body. Today's avatar exported 190 units tall, which fits a body 190 mm tall. Others who use MD set the unit to centimetres for a MetaHuman: Epic [13] and Virtual Filmer [14]. One Daz user whose T-pose figure got this same error said MD found the points once the scale was right [15]. **First step: run the same job again at scale 10.**
2. **MD documents no definition of the pose.** It says only "T or A pose" (OBJ), "humanoid avatars only" (FBX and DNA), and a biped with two arms, two legs and no tail in an A- or T-pose for the fitting suit [1][2][4]. It gives no arm angle, palm, facing direction, size range or skeleton rule. It recommends Y up, outward normals, at most 70,000 triangles, and a symmetric mesh and joints [5].
3. **The API cannot create points.** The 2026.1 program can only list them, assign them and nudge pieces [10][11]. It can **load** an .avt that has points (`ImportAvatar`; measured on 2 October with MD's stock avatar: 110 points, 4.4 s, no dialog) and **save** one (`ExportAVT`). So one GUI step that yields an .avt with points (the DNA import, or points made by hand in the Avatar Editor) serves every script afterwards.
4. **DNA importer:** File ▶ Import ▶ DNA takes the body and head .dna and gives one avatar with joints. You choose the unit by hand; automatic points and a fitting suit are options [9]. There is no API call for it. CLO's pages do not say whether it can be saved as .avt. Two MetaHuman cases are known to be locked: CLO's own MetaHuman bodies and LiveSync imports [8][20][21]. So test it once, with a .zprj as the fallback.
5. **Bind pose:** a MetaHuman's bind pose *is* the reference A-pose our body is exported in. The cleanest and cheapest route is to simulate in that pose, so there is nothing to return. Epic's target for MetaHuman clothing is exactly this: meshes in the standard A-pose, skinned to the MetaHuman skeleton [22]. CLO's own rigging tool recommends rigging in the bind pose [23]. If MD must arrange in another pose, bring the avatar back to the bind pose **inside MD with the simulation running**, so the cloth settles again. Un-posing in Blender is the last resort.

## What was measured today (MD not opened)

- **The body FBX is not static geometry.** MH_TomL1_FullBody.fbx (5.8 MB, binary) contains a skeleton and skin weights. Its byte strings show about 680 "LimbNode" mentions, 1,368 "Cluster", "Skin" deformers and BindPose entries. Its UnitScaleFactor is 1.0, which is centimetres (M).
- **What MD exported** (avatar-check.obj, export scale 1.0):
  - 70,612 vertices and 127,862 triangles, almost twice CLO's recommended 70,000;
  - Y up, facing +Z (toes at +23.5, heels at −7.2);
  - 189.9 units tall, with the hands 114.8 apart at a height of about 95 to 103;
  - arms about 50 to 55° below horizontal, read from width slices (shoulder estimated near height 150, half-width 18) (M).
- **MD's reply to the import:** `GetAvatarMeasurements(0)` returned an empty list and `GetArrangementList()` returned 0 points (F:/LedgerTools/md-jobs/out/import_body.json) (M).
- **The 2 October evidence on scale** [12]:
  - tools/md/jobs/grow_drape.py and swap_body.py set `scale = 10.0` with the note "the bodies are in centimetres, read as millimetres otherwise";
  - they also set `bSizeAndPoseFromAvatar = False`, noting that True (the default) "read the incoming body ten times too small";
  - learn1 (1 Oct, Ron's body, points and fitting suit on) and avatar_try (2 Oct, arms at 52.6, 45 and 35°) set no scale, and all came back with 0 points (F:/LedgerTools/md-bridge/outbox).
- **The size MD held today is inferred, not measured.** The docs do not say which way the export `scale` works [10]. A 190 mm avatar is the reading that fits both the 2 October finding and today's file (I).

## 1. What MD requires for automatic arrangement points

**What the docs say**
- OBJ: Load as Avatar ▶ Add Arrangement Points & BVs. It works properly only when the OBJ is in a T- or A-pose, and otherwise shows the exact error we got [1]. CLO says the same [3].
- FBX: "Automatically Add Arrangement Points", for humanoid avatars only. Scale is either a number or a chosen unit [2].
- Fitting suit at import: the avatar must be a custom biped (two arms, two legs, no tail) in an A- or T-pose [4].
- CLO's avatar rules [5]:
  - required: Y up and outward-facing normals;
  - recommended: an A- or T-pose, at most 70,000 triangles, a symmetric mesh and joints, and CLO's joint names for IK;
  - not supported: Dual Quaternion and Weight Blend skinning;
  - CLO "strongly recommends" ticking automatic points and fitting suit on import.

**What the docs do not say:** any arm-angle range, palm direction, leg spread, facing direction, size range, or whether the fit uses the file's joints. Users in a T-pose report the same error with no official answer (comments of 2020 and 2023 on [3]; a CLO-SET post of 21 December 2025 [16]).

**OBJ against FBX:** both offer the option, and an OBJ has no skeleton, so joints are not needed to *ask* for points (D). Bounding volumes hang between two joints [6][7], so for an OBJ MD must make its own (I). Whether a skeleton in an FBX helps or hinders the fit is not documented (UNVERIFIED). An earlier note found a 139 MB arrangement model and an AI runtime in the install. That suggests a trained fit rather than an angle check, which would also explain why a doll at a tenth of human size fails (I).

**Licence:** the fit is not one of CLO's listed "AI features", which are the texture, graphic and pose generators and the pattern drafter [17]. So the licence note's "no AI features" rule does not catch it (I).

**Our body against the list:** Y up ✓; facing +Z (the way DAZ figures face, after which MD's "cm (DAZ Studio)" unit is named; I); MetaHuman's A-pose, about 50 to 55° down; head on; 127,862 triangles (over the recommendation); probably a tenth of its true size.

## 2. Points without the automatic fit

- **API (the 2026.1 program's own list [11], and the docs [10]):**
  - The only arrangement calls are `GetArrangementList`, `GetArrangementOfPattern`, `SetArrangement`, `SetArrangementPosition`, `SetArrangementOrientation` and `SetArrangementShapeStyle`.
  - No call creates or loads points or bounding volumes (.arr or .pan), fits them to an avatar, edits joints or rigs.
  - `ImportAvatarMeasurement(csv, avt, opt)` loads a measurement CSV onto an .avt, which is for sizing, not points (D, by its docstring).
  - `SetArrangementPosition` only moves a piece relative to an existing point. On 2 October it moved nothing until `SetArrangement` was run again [12].
- **What the API can do with an avatar file:**
  - `ImportAvatar(path, options)`: CLO's own scenario uses it [10], and it was measured on 2 October with MD's stock avatar (110 points, no dialog) [12].
  - `ExportAVT(path)` saves the current avatar.
  - `ImportZprj` with `bLoadAvatar` / `bLoadGarment` loads a project's avatar alone [10].
  - An .avt holds the model, skeleton, size, pose, bounding volumes and points [6][8].
- **By hand, once:** Avatar Editor ▶ Arrangement [6][7].
  - Add bounding volumes: start and end joint, shape, height and radii.
  - Add points: volume, X, Y, offset and wrap direction. Names ending _L and _R are mirrored.
  - Save as .pan and .arr; an .arr "can be used to apply Arrangement points to an *.OBJ avatar".
  - Fit to Avatar (All) re-fits the volumes to another avatar's joints. Save As ▶ Avatar.
  - MD posted an official video, "Set up Arrangement Points for Custom Avatars" (18 Dec 2025); it was not watched.
  - All our MetaHumans share joint names, so one .pan/.arr made on Tom should fit the other bodies with Fit to Avatar (I).
- **What others do with their own bodies:**
  - CLO: automatic points and fitting suit on import, then the Avatar Editor if they fail [5].
  - Epic's UEFN sweater: a MetaHuman imported with automatic points on and the unit "cm (DAZ Studio)" at 100% [13].
  - Virtual Filmer: choose centimetres, not millimetres; if MD cannot make the fitting suit, make it by hand [14].
  - Auto Convert to Avatar, "Rigging Only" (A-pose recommended), adds MD's own joints and saves an .avt [18]. It would replace our skeleton with MD's, so it is not wanted for skinning (I).
- **Licence:** placing pieces with CLO's stock .arr/.pan puts nothing of CLO's in the game (I). The SPEC's "no CLO avatar" rule rules out arranging on CLO's 18 MetaHuman bodies (encrypted .avte files [21]).

## 3. The MetaHuman DNA importer (2025.2 and later)

- **What it does** [9]:
  - Main Menu ▶ File ▶ Import / Import (Add) ▶ DNA; load the Body and Head .dna.
  - Options: Unit (pick a unit and type a scale), Auto Add Arrangement Points, Auto Create Fitting Suit (both "for humanoid avatars only"), and Axis Conversion.
  - The result is one seamless head-and-body avatar with joints you can pose and key. .mtn motions are not supported.
  - CLO's page is the same.
- **Pose:** not stated. The DNA format stores the joints in the bind pose [19], and Epic's MetaHumans come in "the standard MetaHuman A-pose" [22]. So the DNA avatar should stand in the same pose as our FBX (I, UNVERIFIED).
- **Units:** chosen by hand in the dialog, not read from the file (D); centimetres for a MetaHuman.
- **Where the .dna comes from:**
  - Unreal 5.8: Export DNA on the DNA asset; files from MetaHuman Creator are written as Left, Up, Front [19].
  - Creator's DCC Export: head DNA, body DNA and textures [19].
  - The 5.8 Python call named in the 2 October note.
- **Script:** no DNA call exists in the 2026.1 program [11]. The import is one GUI step by Jafar.
- **Saving it:** the docs allow Save As ▶ Avatar for any avatar [8]. Two MetaHuman limits are documented, and neither names DNA imports (UNVERIFIED):
  - CLO's 18 MetaHuman bodies are .avte files that "cannot be exported" [21];
  - a MetaHuman sent over LiveSync can be saved only as ZPRJ [20].
  - Plan for the step:
    - right after Jafar's import, a job calls `ExportAVT`;
    - if that fails, he saves a .zprj and jobs load its avatar with `ImportZprj` (`bLoadAvatar` true, `bLoadGarment` false);
    - then `GetArrangementList` checks that the points survived the reload.
- **No user report** was found of the DNA importer's points working or failing.
- **Check before use:** the DNA avatar is MD's rebuild, not our exported FBX. Compare the two in Blender (same pose, within a few mm) before any pattern is cut (I).

## 4. From the simulation pose to the game's bind pose

**The clean route: nothing to return**
- The MetaHuman bind pose is the reference A-pose our body FBX is in.
- Epic ships MetaHuman clothing as meshes in the standard A-pose, skinned to the MetaHuman skeleton [22]. CLO's EveryWear says to rig in the bind pose, since rigging in another pose can leave faults when weights are edited [23].
- So simulate on the body as exported, export the garment, and transfer weights in Blender from the same body in the same pose. That is the 30 September ruling: weights from his body, joints fixed by hand.

**If MD can only arrange in another pose, return it inside MD while simulating**
- The documented ways:
  - load a .pos: simulation turns on and the avatar moves gradually to the new pose, with the garments simulated along (`ImportPose` is in the API) [25];
  - "Reset Joint" on an FBX avatar with joints [18];
  - EveryWear's "Switch to Bind Pose" [23];
  - morph to an OBJ of the same mesh in the bind pose. Morphing keeps the avatar's final shape without distortion, but large pose changes can drop garments, so go in stages [25].
- The cloth settles again by physics, so no skinning faults are baked in.
- Whether each of these works on our FBX avatar *by script* is UNVERIFIED. The API documents only object types 0 (avatar) and 1 (trim) for imports, so morph targets by script are unknown.

**Un-posing in Blender (skin to the posed skeleton, then rest), last resort**
- Blender's manual warns that applying a pose as the rest pose resets skinned meshes to their undeformed shape, so the work is: copy the armature, make the simulation pose its rest, bind the garment with weights from the body in that pose, pose the copy back to the bind pose, apply the deformation, then bind to the real skeleton [26].
- Linear skinning distorts most at the shoulders and armpits, exactly where a jacket folds. The folds were also simulated for another arm angle. Use it only for a few degrees (I).

**MD's own skinned export (EveryWear) [23]**
- What it is: a free beta plug-in while in beta; CONNECT ▶ EveryWear; FBX export to disk since 2025.2 [24].
- What it does:
  - copies the body's weights to the garment, with a limit on joints per vertex;
  - offers weight and sculpt brushes and Switch to Bind Pose;
  - exports FBX for a "General" platform, with or without the avatar.
- What it needs:
  - an avatar with joints, and only one avatar in the scene;
  - no simulation after rigging, because any simulation deletes the rigging;
  - GUI only (no API call);
  - its preparation page asks for Auto Fitting on a fitting suit.
- Not known (UNVERIFIED): whether it keeps the MetaHuman FBX's own weights and joint names on export.
- Our step 4 is already scripted in Blender. EveryWear would add clicks and checks for nothing we lack (I).

**Verdict:** the least work and the cleanest garment come from simulating in the bind pose. Next best is a pose change inside MD with the simulation running. Blender un-posing is the last choice.

## Recommended route

1. **One job, no new click: the same import at scale 10.** Settings: `scale = 10.0`, `bSizeAndPoseFromAvatar = False`, `bAddArrangementPoints = True`, `bAutoCreateFittingSuit = True`.
   - It passes when `GetArrangementList()` returns points.
   - Check the size too: export the avatar alone at scale 1.0 and expect about 1,900 units, if the export is in mm. Compare that OBJ with the FBX in Blender to learn the export's scale direction once.
2. **If points come:** `ExportAVT` to F:/LedgerTools/bodies/MH_TomL1/MH_TomL1.avt. Every later job uses `ImportAvatar` on that file, checking the point count after loading. Do the same for each body.
3. **If none come:** a second try at scale 10 with a body under 70,000 triangles (a lower level of detail, still in MetaHuman's A-pose). That is the two-tries limit for this method.
4. **Then Jafar's one GUI step:** File ▶ Import ▶ DNA with Tom's body and head .dna (exported from Unreal 5.8 by script), unit cm, both options ticked. A job then saves the .avt (or he saves a .zprj), and Blender confirms it matches the game body.
5. **Last:** points made once by hand in the Avatar Editor on Tom's FBX avatar (volumes on MetaHuman joints), saved as .pan, .arr and .avt, and fitted to the other bodies with Fit to Avatar (All).
6. **Garments:** simulate in the body's own reference pose and export it there. Skin in Blender from the same body. Return a pose only if step 4 or 5 forces one, and then inside MD.
