## Findings

### Q1. What makes FindFirst time out
1. **UIA waits for the provider, with limits.** IUIAutomation2 ConnectionTimeout: "The default connection timeout value is two seconds"; it is the time UIA waits for a provider to respond to a request for an element. TransactionTimeout: "The default transaction timeout value is 20 seconds. Because some operations require the provider to process hundreds of elements, the provider might need a significant amount of time". Both settable in milliseconds. (D) https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nf-uiautomationclient-iuiautomation2-put_connectiontimeout and https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nf-uiautomationclient-iuiautomation2-put_transactiontimeout (both page dated 2018/2024, read 16 Nov). These are the **COM client's** knobs. Whether the managed System.Windows.Automation client used by the script honours or exposes them was not found (U); the managed class has no timeout property in the FindFirst page read.
2. **Search scope matters.** Microsoft: "When searching for a top-level window on the desktop, be sure to specify Children ... not Descendants. A search through the entire subtree ... could iterate through thousands of items." (D, for the desktop case; same logic for a large window, I) https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.automationelement.findfirst (read 16 Nov). The tree is built on demand, "might contain thousands of elements"; "Parts of the UI Automation tree are built as a client needs them" (D) https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-treeoverview (read 16 Nov). FindFirst with Descendants and a Name condition forces the provider to answer one cross-process query per visited element until a match (I).
3. **Qt turns accessibility on lazily, on the first client query.** In qtbase's Windows UIA plugin, `handleWmGetObject` (the reply to a UIA client's first window request) calls `accessibility()->setActive(true)` and sets `m_accessibleActive = true`; it ignores requests while the app is starting up or closing down; events are dropped until active. (D, source on the dev branch) https://raw.githubusercontent.com/qt/qtbase/dev/src/plugins/platforms/windows/uiautomation/qwindowsuiaaccessibility.cpp (read 16 Nov; dev branch, Qt 6 version used by Marvelous 2026.1 not known, U). Marvelous is Qt 6 per the script header (U: not confirmed from the install). So the first FindFirst on a fresh Marvelous is also what switches Qt accessibility on, and it then builds provider objects for the tree while the client waits (I).
4. **Qt's provider can be very slow on large or busy trees.** Search-result summaries only (the bug pages were not read; bugreports.qt.io redirects to qt-project.atlassian.net, which returned only the word "Jira"; bugreports-test.qt.io did not resolve): QTBUG-100997 (table freeze, provider walks every child, Qt 5.15 to 6.2), QTBUG-128477 (6.7.2, combobox hang for minutes), QTBUG-113860 (UI hangs of seconds on state change), QTBUG-82930 (hit-test on tree hangs). (U, search summary only.) Search listing: https://bugreports-test.qt.io/browse/QTBUG-100997 etc. Common thread per the summary: per-child traversal in `QWindowsUiaMainProvider`.
5. **Another UIA client or a race can disturb Qt's provider.** Qt accessibility list thread: a Qt 5.15 app crashed when UIAutomation was used from several threads; Qt's Sæther suggested non-atomic reference counting in `QWindowsUiaMainProvider` "could" be the cause; never confirmed (D for the thread, root cause U). https://lists.qt-project.org/pipermail/accessibility/2020-December/000114.html (read 16 Nov). Relevant only if another UIA client (Narrator, a screen-reader, another tool, Claude's own harness) ran at the same time (U that any did).
6. **A busy GUI thread.** The script checks `Process.Responding` before starting, which only says the message loop pumped at that instant. A provider call runs on the app's GUI thread, so a loading Marvelous (the 3D viewport, library, licence check, plug-in scan after launch) can delay answers beyond the timeouts (I; no Marvelous or Qt page states this).
7. **Same error elsewhere, fixed by a different search.** One Stack Overflow thread reports the same "Operation timed out" from FindAll/FindFirst on a freshly loaded WebView, fixed by replacing both with a TreeWalker loop (via search summary; page not read, U). https://windows-hexerror.linestarve.com/q/so47820560-windows-uiautomation-sometimes-hangs-other-apps and https://kiwix.lema.org/stackoverflow.com_en_all_2023-11/questions/47820560/windows-uiautomation-sometimes-hangs-other-apps (seen in search only, 16 Nov).
8. **The managed client is legacy.** Search summary: the System.Windows.Automation namespace is described as legacy, with the COM IUIAutomation recommended for new work (the exact Microsoft wording was not read, U). The .NET page read (FindFirst) points to the Windows Automation API page for the latest.

### Q2. Which fits the facts
- **Facts:** two timeouts (8 Nov, 16 Nov) and one success (9 Nov), the success 21 s after launch of a fresh Marvelous; the failure 16 Nov was on a fresh Marvelous with its window up 5 s after launch.
- **Fresh-versus-long-running is not the split.** 9 Nov, a success, was a fresh launch too. The difference in the logs is the time from launch to the start (21 s ok; the failing call ran long, the result written 92 s after launch) and nothing else known. Time of day or load on the PC at 10:19 is not logged (U).
- **Fits (I, none confirmed):**
  a. Descendants search over the full main window tree (viewport, panels, lists) with a pending first activation of Qt accessibility: the call exceeds a UIA timeout when the tree is large or the GUI thread is busy. Consistent with the intermittent failures and with items 2, 3, 6 above. The code path is the heaviest one in the script (the "Plugins" search is Descendants).
  b. A busy GUI thread after launch (items 3 and 6): consistent with 16 Nov being seconds after the window appeared; but 9 Nov was equally fresh and worked.
  c. A second UIA client at the same time (item 5): possible; no evidence in the logs.
- **Does not fit:** a "huge viewport tree" alone does not explain 9 Nov's success unless the tree differs between runs (I). A Qt-wide lack of UIA support does not fit: the same script invoked the menu on 30 Oct, 2 Nov, 9 Nov.
- **The script's hang past 6 minutes** (second 16 Nov run): the PowerShell call has no outer time limit; TransactionTimeout is 20 s per call, but a Descendants search makes many calls, so a total of minutes is possible (I). No source gives the total behaviour of a FindFirst that is retried per element.
- **Gap that would settle it:** the log does not name which call threw (the root FindFirst or the Descendants one), nor the elapsed time of the failing call. Adding that to the log is the cheapest next datum (a suggestion on the data, not a decision).

### Q3. Mitigations that keep to one menu item, no mouse or keyboard
Each is documented as an API behaviour; none was found proven for Marvelous or Qt 6 menus (U for effectiveness).
1. **Walk narrower, by Children.** Search Children of the main window for the MenuBar, then Children of the menu bar for "Plugins", instead of Descendants from the window. Source: FindFirst remarks (Children for top level; Descendants can iterate thousands) https://learn.microsoft.com/en-us/dotnet/api/system.windows.automation.automationelement.findfirst; "scoping ... only direct children" https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-treeoverview; Microsoft's own find example uses `TreeScope_Children` https://learn.microsoft.com/en-us/windows/win32/winauto/uiauto-howto-find-ui-elements (all read 16 Nov). Qt menu-bar items appearing as direct children of a menu bar element is I (not read in Qt docs).
2. **TreeWalker (Control or Raw view walker) over Children.** The StackOverflow thread above reports it removing the same timeout (U, search summary). Microsoft: TreeWalker "can result in cross-process calls and is not as efficient as ... FindAll or FindFirst" (D) https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nn-uiautomationclient-iuiautomationtreewalker (read 16 Nov).
3. **Raise the timeouts through the COM client** (IUIAutomation2 ConnectionTimeout, TransactionTimeout, milliseconds; defaults 2 s and 20 s). Requires COM IUIAutomation via CoCreateInstance from PowerShell/C# (IUIAutomation2 minimum Windows 8). Pages: the two timeout pages above plus https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nn-uiautomationclient-iuiautomation2 (read 16 Nov). The managed client in use has no such property in the pages read (U).
4. **Cache requests**: IUIAutomation::CreateCacheRequest and the `...BuildCache` TreeWalker methods fetch properties and patterns in one cross-process call instead of one per property. https://learn.microsoft.com/en-us/windows/win32/api/uiautomationclient/nf-uiautomationclient-iuiautomation-createcacherequest and the TreeWalker page above (read 16 Nov). The pages read do not quantify the saving (U).
5. **Warm-up query, then wait and retry.** A cheap first query (for example the Children-only window search) triggers Qt's one-time `setActive(true)` (item 3 above, D for the activation, I for the benefit); wait for the app to finish loading and retry the narrow search. No page found describes this as a published pattern for Qt; it follows from items 1 and 3 (I).
6. **Wait for the app to settle before the first query**: CPU idle or the main window's title/class stable, the existing `Responding` check being only a single sample. No source found naming a CPU-idle test for UIA clients (U). Reading CPU time of the Marvelous process over a few seconds needs no input to the app (I).
7. **One UIA client at a time; calls off any UI thread.** Qt list thread above (item 5) and Microsoft's threading note: client calls on a separate thread if the client touches its own UI https://learn.microsoft.com/en-us/dotnet/framework/ui-automation/ui-automation-threading-issues (read 16 Nov). The script is a console process with no UI of its own, so the second point probably does not apply (I).
8. **Outer time limit on the whole call** so that a hang ends (the 6-minute hang): run the search in a job or separate process with a kill after N seconds. General practice (I); no source read.
9. **Switch to the COM API or a wrapper (FlaUI UIA3)**: from search summaries only (U); FlaUI issue seen in search: https://www.github.com/FlaUI/FlaUI/issues/614 (not read).
