  TWO STAMP-ONLY RERUNS OF FOUR EXAMINED. The first version of this paragraph
  said one of one, which was true when written and is superseded rather than
  deleted, because a denominator that grows is the reading and not an
  embarrassment. The fault is not that the page regenerates: it is that a run
  which measured no change is indistinguishable on disk from one that did, and
  half the runs in this series measured no change.

  WHY IT COSTS ANYTHING AT ALL. The Stop hook asks for a clean tree, so every
  stamp-only rerun produces a commit whose entire content is a clock reading.
  Over a night of hourly ticks that is a run of commits saying nothing, in a
  history where the message is supposed to be the record.

  THE STAMP ITSELF IS NOT THE PROBLEM AND MUST NOT BE DELETED. A reader needs
  to know how old the page is, and a page with no stamp cannot tell a fresh
  rebuild from a stale checkout. The problem is writing the file when only the
  stamp would change.

acceptance: a rerun that finds no change leaves STATUS.md and dashboard.html
  BYTE-IDENTICAL on disk, and says so on its done line with a count rather than
  silently: how many of the files it was asked to write it actually wrote, and
  how many it left alone because nothing moved. A rerun that DOES find a change
  still rewrites both files and still updates the stamp, and that is the
  accepting case to test first: plant a real change (a card under WAITING, a new
  queue file) and prove the stamp moves. The rejecting case is two consecutive
  runs over an unchanged tree leaving the same bytes.

  THE OBVIOUS IMPLEMENTATION IS THE ONE TO AVOID BLIND: comparing the whole
  rendered text against the file on disk will never match while the stamp is
  inside that text. Render with the stamp held out, compare that, and only then
  decide whether to write the stamped version.
